## Completed live cases

The corrected release binary replaced only `/usr/bin/agent-seat-x11`. Its
installed checksum matched the release build byte for byte. Restarting only
`agent-seat-x11-input.service` created provider PID 2409915 and the following
state:

```text
ActiveState=active
SubState=running
Seat disabled (generation 0).
```

Running the operator command with `DISPLAY=:0.0` against a provider started
with the session's `DISPLAY=:0` returned the same disabled state. This proves
that control discovery follows the selection-bound advertisement rather than
hashing a launcher-specific spelling of `DISPLAY`.

An installed `agent-seat-mcp` 0.1.3 process then made only `seat_status` calls
against the fixed private provider socket:

1. While disabled, the provider refused the handshake with code `refused` and
   diagnostic `operator seat is disabled`.
2. `agent-seat-x11 seat enable` returned `Seat enabled (generation 0)`.
3. A fresh MCP process completed `seat_status` with `status=ok`,
   `assurance=tier0`, and a nonzero session identity.
4. `agent-seat-x11 seat disable` returned `Seat disabled (generation 1)` while
   the same provider PID and active service remained present.

No input operation, application launch, window-management request, physical
device access, package installation, or display-session transition was part of
these cases.

   `Seat disabled (generation 0)`.

If the user manager automatically starts a provider through separately
configured session startup, that is acceptable only when it is a new process
and remains disabled at generation zero. No startup, greeter, authentication,
unlock, or return-to-session path may run `seat enable`.

This case tests provider lifetime and volatile authorization only. It does not
test whether LightDM withdraws raw-input eligibility before its greeter accepts
credentials, and it cannot pass the separate T5 lock-ordering gate.

# Tier 0.5 verification record

Status: provider lifecycle verified on the live reference host, 2026-08-09.
The explicit runtime gate and one deliberate LightDM/Openbox logout/relogin
cycle pass. This is not evidence for the separate trusted-lock ordering gate.

## Completed live cases

The corrected release binary replaced only `/usr/bin/agent-seat-x11`. Its
installed checksum matched the release build byte for byte. Restarting only
`agent-seat-x11-input.service` created provider PID 2409915 and the following
state:

```text
ActiveState=active
SubState=running
Seat disabled (generation 0).
```

Running the operator command with `DISPLAY=:0.0` against a provider started
with the session's `DISPLAY=:0` returned the same disabled state. This proves
that control discovery follows the selection-bound advertisement rather than
hashing a launcher-specific spelling of `DISPLAY`.

An installed `agent-seat-mcp` 0.1.3 process then made only `seat_status` calls
against the fixed private provider socket:

1. While disabled, the provider refused the handshake with code `refused` and
   diagnostic `operator seat is disabled`.
2. `agent-seat-x11 seat enable` returned `Seat enabled (generation 0)`.
3. A fresh MCP process completed `seat_status` with `status=ok`,
   `assurance=tier0`, and a nonzero session identity.
4. `agent-seat-x11 seat disable` returned `Seat disabled (generation 1)` while
   the same provider PID and active service remained present.

No input operation, application launch, window-management request, physical
device access, package installation, or display-session transition was part of
these cases.

Before asking the maintainer to enter credentials at the LightDM greeter, the
root-only exact `agent-seat-activity-enroll stop --uid 1000` transaction was
run. Both UID-bound broker and guard services and both sockets then reported
`inactive/dead` with no service PID. Enrollment and provider policy were left
unchanged. The logout/relogin lifecycle check therefore cannot expose greeter
keystrokes to the experimental raw-input broker; it intentionally tests only
provider lifetime.

## Completed LightDM logout/relogin case

The pre-logout evidence is:

```text
provider PID: 2409915
session ID: 68
seat: seat0
VT: 1
runtime gate: disabled, generation 1
activity broker and eligibility guard: inactive/dead
```

The maintainer logged out normally through the LightDM/Openbox session and
logged in again. Before any new provider start, the following public
observations held:

1. `/proc/2409915` was absent; the old provider did not survive the session.
2. The old provider selection and both old sockets were absent.
3. The activity broker and eligibility guard remained inactive with no service
   PID and no socket.

The provider journal records that LightDM's X server closed the old X11
connection at logout. The provider consequently exited status 1 and systemd
retained an honest `failed` diagnostic; no restart occurred because the unit
has `Restart=no`. Resetting that diagnostic and explicitly starting the same
unit created a new provider, without enabling it:

```text
post-login session ID: 71
provider PID: 2427887
ActiveState=active
SubState=running
Seat disabled (generation 0).
```

A fresh installed `agent-seat-mcp` 0.1.3 process then called only
`seat_status` through the fixed provider socket. Its opening handshake was
refused with code `refused`, retry `never`, and diagnostic
`operator seat is disabled`. No new explicit enable was performed. All five
predeclared pass observations therefore hold.

If the user manager automatically starts a provider through separately
configured session startup, that is acceptable only when it is a new process
and remains disabled at generation zero. No startup, greeter, authentication,
unlock, or return-to-session path may run `seat enable`.

This completed case tests provider lifetime and volatile authorization only.
It is evidence for this exact released LightDM/Openbox/systemd combination,
not for other launchers. It does not
test whether LightDM withdraws raw-input eligibility before its greeter accepts
credentials, and it cannot pass the separate T5 lock-ordering gate.
